description: Client components, request safety, and what runs where

Expressive components are **client components**. They render fine on the server - `renderToString`, and the SSR pass Next.js gives every client component - without touching the DOM. What they are not is server-resident state: nothing here runs inside React Server Components themselves.

<br />

## 'use client'

In an App Router project, a file that defines or uses a Model class is client code. `@expressive/react` registers the React host as an import side effect, and it must be loaded in the client bundle - a module evaluates once, so importing it beside your classes is harmless and keeps every client entry covered:

```tsx
'use client';

import '@expressive/react';
import { Component } from '@expressive/mvc';

export class Sidebar extends Component {
  open = false;

  render() {
    const { open } = this;

    return <aside data-open={open} onClick={() => (this.open = !open)} />;
  }
}
```

Server components compose these normally - fetch on the server, pass serializable props down, and let the instance take over from there. As with any client component, give the client the same inputs the server rendered with, and hydration lines up.

<br />

## What runs where

| | Server render | Client |
| --- | --- | --- |
| constructor, field initializers | ✓ | ✓ |
| `new()` | ✓ | ✓ |
| `render()` | ✓ | ✓ |
| effects declared in `new()` | never | ✓ |
| `on({ ready })` | never for a host-owned instance | ✓ |
| `await state.get(() => {})` | pending for a host-owned instance; rejects once it is destroyed | ✓ |
| `new()`'s returned teardown | at garbage collection, or when the request's `Context` pops | ✓ |

The last four rows are the rules that matter. There is no unmount on the server, so a resource opened in the `new()` body - a socket, a subscription, a file handle - outlives the response. An effect declared in `new()` waits for the owning component to commit, which never happens on the server, so that is where such work belongs.

<br />

## Ending a request

Without an unmount, the adapter destroys server-rendered instances whenever they are garbage collected. To end a request at a moment you choose, render it within a `Context` and pop it:

```tsx
import { Component, Context } from '@expressive/mvc';

const request = Context.root.push();

try {
  html = renderToString(
    <Component for={request}>
      <App />
    </Component>
  );
} finally {
  request.pop();
}
```

`pop()` destroys every instance the render built: `new()` teardowns run, and anything awaiting a host-owned instance's readiness rejects with `is destroyed.` instead of waiting indefinitely. For a streaming render, pop when the stream ends. `Context.root.push()` keeps process-wide instances in reach; pushing Models into the request context provides them to the whole render.

To await readiness during a server render, await an instance the server built itself - `Model.new()`, or one passed as `<Component for={instance}>`. Those never wait on a commit.

<br />

## Three rules for request safety

**Request state goes in a `<Component for>`.** Each render builds its own context, so provided instances are isolated - one request never sees another's.

**An instance held in `Context.root` is process-wide - and on the server, that means shared across requests.** Root suits process state: config, feature flags, a warmed cache. Keep per-request data out of it; provide it with `<Component for>` instead.

**Resources belong in an effect or the framework's request scope, never the `new()` body.** An effect never fires on the server, so client resources stay client-side for free. Anything the server itself must open and close belongs to the request handler, which actually has a close.

<br />

## The Router on the server

`@expressive/router` targets client-routed apps. Each render's `Router` is its own, so paths never bleed between requests. To render a specific request's path, provide a `Router` per request:

```tsx
<Component for={Router} path={request.path}>
  <App />
</Component>
```

In a Next.js app the framework owns the URL regardless.
